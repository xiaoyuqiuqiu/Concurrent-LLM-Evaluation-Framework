在顶栏增加一个本地测试并发页面，自动读取，本机的硬件信息，包括cpu，内存大小，内存频率，显存大小，显存速度，显存带宽， Gpu核心

要准确知道在你这套硬件+模型+LLM Studio 环境下的**最佳 QPS（Queries Per Second）**，**没有直接的计算公式**，因为 QPS 是硬件算力、显存带宽、模型结构、请求特征（输入/输出长度）、推理引擎调度策略共同作用的结果。但你可以通过**理论估算 + 系统化压测 + 延迟/吞吐权衡**来找到实际可用的最佳值。下面给出可落地的完整方法：

---
### 🔍 一、先理解 QPS 的本质限制
LLM 推理分为两个阶段，瓶颈不同：
| 阶段 | 计算特征 | 主要瓶颈 |
|------|----------|----------|
| **Prefill（处理输入 prompt）** | 高度并行，矩阵乘法密集 | GPU 算力（TFLOPS）、Tensor Core 利用率 |
| **Decode（逐 token 生成）** | 自回归，每次只生成 1 个 token | **显存带宽**（每次需加载全部权重） |

**单流理论上限（Decode 阶段）**：
```
最大 tokens/sec ≈ GPU显存带宽(GB/s) ÷ 模型权重体积(GB)
```
例：RTX 4090（带宽 1008 GB/s）跑 7B FP16 模型（≈14 GB）→ 约 72 tok/s（单请求）
> 注：实际会打 7~8 折（KV Cache、调度开销、PCIe/CPU 瓶颈等）

**QPS 换算**：
```
QPS ≈ 系统总吞吐量(tokens/sec) ÷ 平均每次请求输出的 token 数
```
若系统压测得 500 tok/s，平均每次生成 50 token → 理论 QPS ≈ 10

---
### 📐 二、理论估算：你的硬件能撑多大并发？
#### 1. 显存容量限制（决定最大 batch size）
```
所需显存 ≈ 模型权重 + KV Cache + 框架开销(10~20%)
KV Cache ≈ batch_size × seq_len × num_layers × hidden_size × 2 × dtype_bytes
```
- 若显存不足，请求会被排队或 OOM，QPS 直接断崖下跌。
- 建议预留 10~15% 显存给 KV Cache 动态增长。

#### 2. 显存带宽限制（决定 decode 吞吐上限）
- GDDR6X ≈ 500~1000 GB/s，HBM2e ≈ 1500~2000 GB/s
- 带宽越高，多 batch 下的 tokens/sec 越接近线性增长（直到算力或调度成为新瓶颈）

#### 3. CPU & 内存的作用
- 主要用于：请求解析、tokenizer、batch 组装、权重 offload（显存不足时）
- 内存频率对 QPS 影响极小，**容量和 PCIe 带宽**更重要
- 若使用 CPU offload，QPS 会下降 3~10 倍

---
### 🧪 三、实测找最佳 QPS 的标准流程
理论只是上限，**必须压测**。推荐步骤：

#### ✅ 1. 准备压测脚本
使用 Python + `concurrent.futures` 或专业工具：
- `llmperf`（OpenAI 兼容接口压测）
- `vllm bench`（若后端支持）
- `locust` / `wrk`（HTTP 接口负载测试）
- 自定义脚本记录：TTFT（首 token 延迟）、TPOT（每 token 延迟）、总吞吐、OOM 率

#### ✅ 2. 控制变量压测
固定以下参数，逐步增加并发数（concurrency）：
- 输入长度（如 512 tokens）
- 输出长度（如 128 tokens）
- temperature/top_p（固定为 0 或 1，避免采样波动）
- 关闭 streaming（或统一开启）

记录每组并发的：
| 并发数 | QPS | TTFT(ms) | TPOT(ms) | 显存占用 | GPU利用率 | 是否OOM/排队 |
|--------|-----|----------|----------|----------|------------|----------------|

#### ✅ 3. 找到“最佳 QPS”
最佳 ≠ 最大。通常按业务 SLA 定义：
- 聊天机器人：TTFT < 1.5s，TPOT < 50ms → 取满足该条件的最高 QPS
- 批量生成：可接受高延迟 → 取 OOM 前或 GPU 利用率饱和（>90%）时的 QPS
- 曲线拐点：QPS 增长变缓、延迟指数上升、或出现请求丢弃的点，即为实际瓶颈
